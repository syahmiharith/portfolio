## The problem

An approved request is a promise to supply something. Stock should change when the items are actually fulfilled, and the record needs to explain what happened if fulfillment fails.

## My role

Request workflow, inventory interface and test setup. Historical project attribution remains in the repository.

## Decisions

### Separate approval from fulfillment

Approval records the requested quantities without deducting or reserving stock. Fulfillment checks availability again. This allows demand to be approved while making the later stock check essential; approval alone does not guarantee supply.

### Commit the whole request together

The fulfillment service updates the request, deducts its items and writes its audit entry inside one database transaction. If the second item is unavailable, the first deduction must roll back too.

The integration test makes that concrete: a request for three paper reams and nine ink units fails when only eight ink units remain. Both original stock counts must survive unchanged.

### Show what the number means

The inventory table puts stock on hand, reserved quantities and stock-health indicators together. Operators can distinguish a physical count from what is available to fulfill.

## Keeping checks reproducible

The test suite covers insufficient stock, repeat fulfillment and partial-update rollback. CI provisions PostgreSQL, applies migrations and runs integration and browser checks. A maintenance change pins the runner to Ubuntu 24.04 for Playwright compatibility instead of following a moving OS image.
