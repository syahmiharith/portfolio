## A stock shortage should be recoverable

An administrator can approve a request before the supplies are available. That creates a product problem as well as a database problem: the interface must explain what approval means, show what is short, and help the operator finish the same request after a delivery.

I developed the existing inventory foundation into a public demo of that complete journey. Visitors get a private, seeded workspace and can try both employee and administrator roles without changing another visitor's stock.

## What I built

I worked across the request workflow, interface, transactional backend, tests and release operations. The result connects Dashboard, Inventory and Requests: request two supplies, review that exact request as the demo administrator, record missing stock, issue the request, and inspect the resulting history. The repository retains the project's original attribution.

## Three decisions that shape the product

### Approval is not a stock movement

Approval leaves stock available to other requests. The interface uses **Approved** and **Issued** consistently, and shows on-hand, held-aside, available, requested and short quantities before issuance. An independent hold example makes the difference between physical stock and available stock visible.

This deliberately avoids promising that approval guarantees supply. Issuance rechecks availability against the current database state.

### A shortage returns the operator to the same request

The featured example requests three reams of paper and three boxes of pens. Paper starts at twelve reams; pens start at one box. The request is short by two boxes of pens.

The operator can record two boxes received with a delivery reference, return to the request and issue it. The expected result is nine paper reams and zero pen boxes, with the receipt and issuance recorded in history. A failed attempt must leave the whole request approved and its stock unchanged.

The role handoff opens the exact request just submitted. Filters and list focus are restored when returning from a detail panel. These details keep shortage recovery inside one task.

### Commit the request as one transaction

The service checks status and lines inside the transaction and processes items in a stable order. Deductions, status, movements and history commit together. If a later line is short, earlier deductions roll back.

Creation, receipt and issuance use idempotency keys. Retrying after a committed write loses its response returns the existing result instead of repeating a receipt or deducting stock twice. PostgreSQL tests cover later-line rollback, requests competing for the last units, concurrent issuance and replay.

## Turn stock numbers into decisions

The dashboard shows open workload, stock availability and seven calendar days of issuance activity. Each number has a defined scope: stock health counts distinct supplies after holds, while request readiness is checked per request. Shared stock is rechecked when issued.

Inventory and Requests use graphical summaries that open the matching records. This makes the charts an entry point into the work. I avoided summing incompatible units or presenting seeded activity as business growth.

## Make a public demo safe to explore

Each visitor receives a server-validated opaque HttpOnly session tied to a workspace and seeded identities. Relationships, reads and writes are scoped to that workspace. Sessions expire after 24 hours, with reset, bounded activity rates and expired-data cleanup.

Preview uses a separate private schema and restricted database login on the existing free Supabase project. The preview login was checked against production and legacy tables: access was denied. This separates data permissions while sharing infrastructure and free-tier quotas.

## Maintain the whole experience

The interface evolved into one shared visual system, including custom dropdowns, a calendar, a compact account menu and problem reporting. Adding the calendar exposed an important interaction: Escape should close the date selection while preserving the request form behind it. A browser regression check protects that behavior.

Releases pass type checking, lint, component checks, PostgreSQL integration tests, browser workflows and a production build. The deployed journey and mobile layouts were checked again on 8 November 2026. Operational work includes expired-workspace cleanup, monitoring and backup/restore checks; implementation and release evidence are linked below.

## Current boundaries

This is a deployed operational demo with synthetic data and simulated employee/admin roles. It demonstrates the workflow and safeguards; it is not evidence of adoption by an inventory team. Unfamiliar-visitor trials and an inventory-operator follow-up remain the next validation step. I make no claim here about time saved, customer usage or business impact.
