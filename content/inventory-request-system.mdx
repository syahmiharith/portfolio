<h2 id="overview">A shortage should be recoverable</h2>

Approval can happen before supplies are available. I developed an existing inventory foundation into a public demo that explains the shortage, records a delivery and finishes the same request. Each visitor gets a private, seeded workspace with employee and administrator roles.

<h2 id="decisions">Three decisions, in the product</h2>

<Decision number="01" title="Approval records demand, not a stock movement" summary="An approved request can still be short. Stock changes only when it is issued." screen="inventory-approval">

The interface uses Approved and Issued consistently. Approval leaves stock available to other requests, so the system checks availability again at issuance. An independent hold example separates physical stock from stock that is available to use.

The role handoff opens the exact request just submitted. Returning to a list restores its filters and keyboard focus.

</Decision>

<Decision number="02" title="Recover inside the same request" summary="Receive missing supplies with a delivery reference, then return to issuance." screen="inventory-receive">

The featured request needs three paper reams and three pen boxes. Paper starts at twelve; pens at one. Receiving two pen boxes makes the request issuable. The expected final stock is nine paper reams and zero pen boxes, with receipt and issuance in history.

The capture shows the delivery form before submission, using a sample reference.

</Decision>

<Decision number="03" title="Issue every line together, or none" summary="Per-line availability explains the decision. One transaction enforces it." screen="inventory-impact">

On-hand, held-aside, available, requested and short quantities are visible before issuance. Status and lines are checked inside the transaction and items are processed in stable order. Deductions, movements, status and history commit together; a shortage on a later line rolls back earlier deductions and leaves the request approved.

Creation, receipt and issuance use idempotency keys so a retry after a lost response cannot repeat a write.

</Decision>

<h2 id="engineering">Build, maintain, verify</h2>

### Numbers that open the work

Dashboard, Inventory and Requests connect workload, stock availability and seven calendar days of issuance to matching records. Stock health counts distinct supplies after holds; readiness is checked per request and again at issuance. I avoided summing incompatible units or presenting seeded activity as business growth.

### A public demo with private workspaces

Server-validated opaque HttpOnly sessions resolve the visitor's workspace and acting identity. Relationships, reads and writes stay scoped to that workspace. Reset, bounded activity rates, 24-hour expiry and expired-data cleanup support exploration.

Preview uses a separate private schema and restricted database login on the existing free Supabase project. Checks denied that login access to production and legacy tables. Data permissions are separate; infrastructure and free-tier quotas are shared.

### Maintenance reaches the interaction details

I own the workflow, interface, backend safeguards, tests and release operations, with the original project attribution retained. A shared visual system now includes custom dropdowns, a calendar, account controls and problem reporting. A browser regression check ensures Escape closes the calendar while preserving its request form.

Releases check types, lint, components, PostgreSQL integration, browser workflows and the production build. Database cases cover later-line rollback, competing requests, concurrent issuance and replay. Operations include monitoring, expired-workspace cleanup and backup/restore checks.

## Current boundaries

These are real product screens with seeded demo data, captured on 9 November 2026. The full deployed journey and mobile layouts were verified on 8 November. This demonstrates implementation and safeguards, not adoption by an inventory team. Unfamiliar-visitor trials and an inventory-operator follow-up remain the next validation step; no time-saving or business-impact result is claimed.
